# 灶眼 AI V1.1：业务对接更新

本次以用户于 2026-10-15 上传、已经修复启动问题的源码为基线。两个 ZIP 的共有业务源码一致；大 ZIP 额外包含部署环境、备份和模拟视频。本更新不替换原 Dockerfile、Compose、Maven 镜像配置、启动脚本和 `.env`。

## 本次实现的链路

| 模块 | 本次代码实现 | 数据口径与边界 |
| --- | --- | --- |
| 视频分析 | 拍摄起始时间、档口计数线快照、任务取消、失败重试、离页后查询、结果视频、关联事件复核 | 原始拍摄时间 + 事件视频偏移确定营业日期；取消后的迟到结果不入库；同一任务/轨迹去重 |
| 摄像头 | 按会话串行读写 Python、启动与逐帧超时、离页停止、空闲清理、所有者校验、保存实时任务 | 默认只保留结构化事件，不保存图像；依旧需要用户授权摄像头，不能自动绕过浏览器授权 |
| 事件台账 | 服务端分页、日期/状态/任务/备注搜索、批量确认/剔除、事件视频定位、退回待复核、关联任务补录 | 确认与审计同事务；批量跨数据域请求整体回滚；同状态重复提交不重复生成审计 |
| 备餐台账 | 选择日期餐次读取/编辑原记录、保留空白实际出餐、模拟样本幂等填充 | 模拟填充只写 SIMULATION，不覆盖已有行；空值不等于 0；未来日期不能填报已核实出餐 |
| 需求预测 | 目标日期、历史列表、刷新恢复、同星期/近期加权基线、样本日期范围、建议写入计划 | 仅使用目标日前同档口、同餐次、同数据域的人工核实数据；至少 3 天；采用建议只改计划量 |
| 日报与看板 | 北京时间 24 小时统计、复核结果统一汇总、事件 CSV 与汇总 CSV | 待复核仍包含在“初步有效事件”中；已剔除不计入；备餐减出餐差额不是实测浪费 |
| 运行环境 | Python/OpenCV/FFmpeg/YOLO 配置探测、任务重启恢复、请求超时、工作区异步竞态保护 | YOLO“已配置”只表示依赖/权重文件可见，不代表类别、精度、硬件适配通过 |

## 首次验证顺序

启动更新后的界面，使用现有账号登录，在**模拟实验**工作区操作。

1. 系统设置检查运行环境和计数线。内置样本的默认线为 `(0.08, 0.54) → (0.92, 0.54)`，方向为 `positive`。修改过线时不要把样本计数必然等于 3 当作断言。
2. AI 出餐监测载入自建模拟视频，填写实际采用的拍摄起始时间，启动分析。默认线下该样本的基准为 3 次正向越线。结果是模拟视觉程序实际计算得到，不能用于宣称食堂识别准确率。
3. 从任务进入人工复核；查看事件、回放视频位置；确认、剔除、批量操作，检查对应审计。按拍摄日期查询日报，确认修改后统计同步。
4. 在备餐页填充明确标记的模拟样本，生成下一目标日期的建议，查看历史与解释；采用建议后确认只变更计划量，没有把计划量自动当成已备餐或核实出餐。
5. 摄像头在本机 localhost 或 HTTPS 打开。授权后用受控模拟目标越线，停止监测并查看其任务与事件。实际摄像头硬件以及真实 YOLO 权重需在目标机器另行验证。

## 新增/扩展的接口

保留 `/api` 前缀、现有身份认证、原路由及旧事件列表接口。

| 接口 | 用途 |
| --- | --- |
| `POST /api/tasks/upload` | 增加可选 `recordedAt`；其他 multipart 字段兼容 |
| `GET /api/tasks?origin=SIMULATION` | 当前数据域最近任务 |
| `POST /api/tasks/{id}/cancel` / `retry` | 取消或重试上传任务 |
| `GET /api/tasks/{id}/video?source=true` | 经过认证读取原始视频；缺省读取标注视频 |
| `GET /api/events/search` | `origin,status,date,taskId,q,page,size` 分页筛选；size 1–100 |
| `POST /api/events/review-batch` | `origin,ids,reviewStatus,note`，单批最多 100 个事件 |
| `POST /api/events/manual` | 扩展 `taskId,offsetSeconds`；关联时校验档口与数据域 |
| `GET /api/audits?origin=...&eventId=...` | 数据域/事件级审计查询，最近 100 条 |
| `GET /api/forecasts?origin=...&mealSlot=...` | 当前餐次最近 30 次预测 |
| `POST /api/forecasts` | 增加 `targetDate`；缺省为北京时间明天 |
| `POST /api/planning/seed-simulation` | `stallId,mealSlot`，跳过已有台账 |
| `POST /api/planning/apply-forecast/{id}` | `overwrite=true` 才覆盖已有计划量，不修改实际字段 |
| `GET /api/reports/summary.csv` | 日报汇总与各餐次备餐记录 |
| `GET /api/system/capabilities` | 只读环境探测，缓存 15 秒，最长探测 10 秒 |

## 数据兼容和升级

数据库仍使用原配置，新增的任务快照、尝试次数、预测日期/区间/方法等字段为可空字段，由现有 `ddl-auto=update` 策略增量更新。不删除原表、原记录、视频、账号配置或 Docker 卷。

旧版视频任务没有计数线快照时可以查看历史，但不允许假设原参数重跑；重新上传后得到完整快照。旧预测没有目标日期时保持可查看，不允许直接写入新计划。已有事件的历史时间不会被静默重写。服务重启时将无法恢复的 QUEUED/RUNNING 任务标记为 FAILED，不伪造已完成；上传任务满足条件后可重试。请避开有视频/摄像头任务正在执行的时段更新。

默认鉴权机制保持不变，重启会让内存中的登录令牌失效，因此更新后可能需要重新登录。此次不是多租户改造，不承诺隔离每个用户的全部业务台账；SIMULATION/REAL 为业务数据域，摄像头控制另有会话所有者校验。

## 更新脚本的保护边界

`Apply-BusinessUpdate.ps1 -Rebuild` 会核验基线和载荷 SHA-256、备份涉及的源文件及现有 MySQL 数据、构建新镜像，然后在一次性容器里用**临时 H2 + 临时存储**执行 HTTP→Java→Python 联调。构建或隔离联调失败时不替换原服务容器。通过后才使用新镜像启动 backend/frontend，再复用原健康检查。

切换阶段失败时尝试恢复原运行镜像；失败信息会保留，不会把它写成升级成功。代码备份、数据库备份和隔离日志保存在项目上一级的 `backups/business-v1.1-*`，这些文件属于本地私有备份，不要公开上传。源码回滚脚本只还原它管理的文件，不自动回滚数据库，也不删除 Docker 卷。

这里的“保护”依赖目标机器上的 Docker/PowerShell 正常执行，不构成未经实际运行的成功保证。完整构建与联调状态见 [本轮测试记录](verification/BUSINESS_V1_1_TEST_REPORT.md)。
