# V1.2：首版业务闭环实现说明

## 本轮范围与交付边界

本轮基于用户提供并已运行的工程及 V1.1，直接修改 React/TypeScript、Spring Boot 和 Python。仍为单档口、固定机位、上传录像＋浏览器实时摄像头。没有重搭技术栈，也没有把多租户、收银、库存、RTSP 中心等后续业务强加到首版。

“业务实现”指本包内已经有相应的界面、接口、持久化及算法参数使用代码；并不意味着完整 Maven/React/Docker 构建、浏览器操作或真实食堂准确率在本开发环境全部验收通过。实际执行证据见 `verification/BUSINESS_V1_2_TEST_REPORT.md`。

真实场景素材与适配餐盘/餐盒的模型权重仍未收到。本包没有训练好的真实模型，不把颜色模拟算法当成真实深度学习识别。本轮完成的是模型调用、目标类别映射检查和模型检查/训练/事件评价工具；不能把“待引入真实模型资产”隐藏成一个已经实现的识别成果。

## 1. 计数规则与特殊情况

基础单位是 **一次独立的容器交付事件**。一个餐盘或独立餐盒通过有向计数线，在两侧满足连续稳定帧要求后记一次。它不是自动确认的餐食份数、顾客人数或销售订单。全部机器事件先进入待复核；只有确认事件进入核实结算。

| 情况 | 实际处理 |
|---|---|
| 同一轨迹停留、来回移动、死区抖动 | 稳定帧＋死区＋同轨迹一次计数；反向移动不当作正向出餐。 |
| 托盘内嵌套餐盒 | 默认 OUTER 只数外层容器；可切换 INNER 数内层盒。保留 NESTED_TARGET 复核提示。几何规则不是对餐食内容的自动理解。 |
| 明确空容器类别 | 仅当所用模型真实具有配置的空容器类别时自动过滤。其余记录 CONTENT_UNVERIFIED，让人工确认或按“空容器”剔除。 |
| 遮挡、低置信、轨迹中断 | 记录 OVERLAP、LOW_CONFIDENCE、TRACK_GAP 等原因；间隔过大不凭空连接越线。 |
| 不同 ID 短时间在近位置越线 | 标记 POSSIBLE_DUPLICATE，不武断删除可能正常连续送出的两份餐。 |
| 同一容器重新装餐后再次送出 | 不宣称能识别“已重新装餐”；轨迹仍相同而被一次计数规则拦住时，人工从视频位置补录新交付。 |
| 同一录像再次上传 | 在同档口、同数据域按文件 SHA-256 查重，返回已有任务；不是靠文件名查重。 |
| 重新编码或剪辑重叠录像 | 不宣称字节哈希能解决此类重复。结算展示覆盖范围并要求核查重叠；需要人工选择合适数据。 |

模型之外的规则在三个语言端采用相同 JSON 契约，包含 ROI、阈值、稳定帧、轨迹间隔、重复预警窗口与距离、嵌套策略、目标及空容器类别。实际推理前裁剪 ROI；标注视频遮盖 ROI 外区域。浏览器实时上传前同样遮盖区域外画面。原始上传录像仍作为经过认证的回看源保留。

设置可用本地图片/视频参考画面拖拽标定，或输入精确坐标。参考画面只在浏览器内用于标定，不会因选择参考文件就自动创建分析任务。计数线必须位于 ROI 内，服务端校验区域大小、参数范围、目标类别去重和餐次时间。

每个任务保存完整规则和计数线快照。修改配置不追溯改变既有任务；失败重试沿用原快照，重新分析建立使用新规则的新版本。

## 2. 一个素材、多个分析版本、一个有效统计版本

`CaptureAsset` 按档口＋数据域＋文件哈希登记素材，保存规范的拍摄起始时间及 `activeTaskId`。首次成功的分析成为有效版本；显式“重新分析”创建新任务但不自动替换原版本。操作人填写切换原因后，才启用新结果。

原事件及复核审计不会被删除。`statsIncluded` 是读模型字段：旧版本可查、可复核，但驾驶舱、日报和结算只使用有效版本。取消/失败的上传任务不进入统计。统计版本切换纳入业务审计。

启动时，对存储目录内仍可读取的旧上传素材幂等补登记哈希；已有同素材多任务时保留最早成功版本作为有效版本。旧源文件已丢失的任务不能凭空恢复哈希，仍按旧记录保留；有问题的历史资料需要结合已有证据复核。旧任务没有可靠时长时，不能伪造视频时间范围，定位补录需要先新建分析版本。

## 3. 完整视频复核与人工补录

即使一个视频没有自动事件，也能从监测任务或事件页打开整段原录像/标注录像。暂停到实际交付位置，填写依据，即可关联 taskId 和 offsetSeconds 补录。服务端用任务的拍摄起始时间计算归档时间，检查视频时长、任务状态和数据域。

补录请求带幂等键；网络失败重试冻结原时间、位置和说明，不重复生成事件。现场无录像的人工记录保留独立入口，不能伪称为可回看的视频证据。

复核支持确认、剔除、退回待复核及批量操作。剔除必须有说明；提供空容器、重复、嵌套重复、遮挡、方向异常等分类，保存状态和分类变化审计。

## 4. 复核 → 餐次结算 → 备餐台账 → 预测

早餐、午餐、晚餐时间可配置；默认 06:00–10:00、10:00–16:00、16:00–22:00 是演示预设，不冒充用户的实际营业时间。统一北京时间、左闭右开，首版不支持跨午夜餐次且不能重叠。

流程：
1. 选择日期、餐次和统一的“每事件对应份数”（默认 1，范围 1–50），生成持久化草稿。
2. 草稿显示确认/待复核/剔除/非统计版本数量，以及相关任务的开始结束、时长是否已知和有效版本状态。
3. 检查所有交付是否完整覆盖，是否存在未拍摄时段、重叠录像或需要人工补录；同时确认所有事件是否适用相同换算。托盘内份数不固定时不要使用统一倍率，应人工核实总份数。
4. 待复核未清零时不能确认；零事件必须单独确认确实零出餐；餐次尚未结束不能确认完整结算；有实际核实量时必须明确允许覆盖。
5. 提交核实依据后，只更新核实出餐及其来源，不改计划备餐或实际备餐。保存草稿、来源摘要、份数倍率、操作人和时间。重复确认同一草稿是幂等的。

草稿有 24 小时有效期，源事件、有效版本、餐次参数或原台账 revision 变化会拒绝过期草稿，要求重算。并发写入按档口行锁串行化；涉及先读后锁的业务事务使用 READ_COMMITTED，避免等待行锁后仍使用旧快照。

后续源事件修改、版本切换或餐次改变，会将已结算台账标为 `verificationStale`。旧核实量保留供追溯，但停止作为新预测和有效差额依据。重新结算，或明确选择“依据独立记录人工重新核实”，才能解除。只有修改计划/实际备餐不会抹掉核实来源。

预测保存候选输入台账快照；只读目标日之前且不处于待重新核实状态的数据。采用历史建议时再次检查它引用的核实量是否已变化。历史均值/加权基线仍是首版方法；展示的范围是样本波动参考，不伪称校准过的概率置信区间。

## 5. 历史查询、权限与统计

- 上传与实时任务统一完整分页；按关键词、拍摄日期、状态、任务模式筛选，支持恢复最近打开任务。
- 事件已有分页；新增完整复核审计分页、业务审计分页、预测历史分页。不再只从最近 6/30/100 条里找旧记录。
- 原有认证与管理员/操作员边界继续使用；配置仍仅管理员可改。操作员复核、版本切换和结算操作留痕，不虚构多用户分租户系统。
- 驾驶舱及日报按完整 24 小时统计。机器初判计数与已确认数分别呈现，容器次数不冒充餐食份数；有效台账差额也不直接叫“实测浪费”。
- 数据域仍严格区分 SIMULATION 和 REAL。模拟样本不覆盖已有台账，不进入 REAL 预测。

## 7. 实际模型资产接入

已有 `scripts/train_yolo.py` 只从本地数据配置和本地基础权重训练；不自动抓网络视频或冒用数据。新增 `scripts/inspect_model.py` 输出本地模型 SHA-256、类别以及与当前规则的匹配情况。必须仅加载受信任模型文件；“类别匹配”不是识别准确率证明。

示例（在 ai-engine 目录，已经安装可选 YOLO 依赖时）：
```text
python -m scripts.inspect_model --weights <本地受信任模型.pt> --rules <任务规则.json> --output model-inspection.json
python -m scripts.train_yolo --data <本地data.yaml> --weights <基础模型.pt> --epochs 50
```

新增 `zaoyan_ai.evaluation` 对人工标注与预测事件按 clip_id 和时间容差一对一匹配，输出事件 TP/FP/FN、Precision/Recall/F1 及计数绝对误差。输入是 JSON 数组，元素形如 `{"clip_id":"clip-a","offset_seconds":3.5}`；空数据不虚构满分。
```text
python -m zaoyan_ai.evaluation --reference annotations.json --prediction predicted.json --output evaluation.json --tolerance 0.5
```

本包未附真实餐盘模型、真实食堂数据或真实测试报告。取得合适的素材和权重后仍需要适配验证，不承诺未经测量的准确率、节约比例或经营效果。

## 8. 更新与回滚

增量包兼容用户上传的运行快照及 V1.1 的已知文件哈希；同一新文件已经更新时跳过，其他本地改动会在写入前停止。补丁不覆盖 Dockerfile、Compose、Maven 配置、原启动修复脚本、私有环境配置或数据库卷。

使用 `-Rebuild` 时，先备份将改的源码和现有数据库；保持旧容器运行，构建新前后端，再用临时 H2 和临时存储运行 `scripts/verify-business.py`。该脚本覆盖真实 Java→Python 调用，但只用自建模拟素材。通过后才切换服务；失败不删除数据库、不假报已经激活。

构建/联调失败时，源码可能已更新，但原服务容器仍是旧版。备份含源码回滚脚本；切换阶段失败会尝试恢复旧镜像。回滚不自动导回数据库快照，避免覆盖更新后新增数据。新增的可空字段和表保留，不执行破坏性删表。原数据库备份属于私有材料，不能再随意上传分享。
